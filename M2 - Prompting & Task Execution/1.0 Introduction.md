### 1. Summary

The [Prompting & Task Execution](https://anthropic-partners.skilljar.com/path/claude-certified-associate-foundations/prompting-task-execution/486636/scorm/2dk4fzu1k4lj) module establishes structured **Description** as a deterministic software engineering discipline rather than an ad-hoc trial-and-error process.

* **Prompt Component Stack**: Effective prompts build upon five distinct structural layers:
  * **Role/Persona**: Defines the domain perspective, expertise level, and tone boundaries.
  * **Task/Instruction**: Clear, unambiguous directives stating the primary objective.
  * **Context & Background**: Operational details, domain rules, and environmental context.
  * **Input Data**: Raw payloads (JSON, text, code) isolated using structural markers (such as XML tags).
  * **Output Formatting**: Rigid structural targets (JSON schemas, tables, Markdown templates) paired with few-shot examples.


* **Task Decomposition**: Multi-step or ambiguous workflows are decomposed into sequential prompt chains or parallel execution streams to mitigate cognitive load and output hallucination.
* **Diagnostic Iteration**: When model output degrades, prompts are audited component-by-component to pinpoint the exact failing layer (e.g., ambiguous input boundaries vs. missing constraints) rather than rewriting the prompt entirely.
* **Task-Specific Strategy Adaptation**: Prompting strategies adapt dynamically across four functional modes:
  * *Analysis*: Enforce chain-of-thought reasoning before outputting final conclusions.
  * *Research*: Require explicit source attribution and negative constraints against unverified assumptions.
  * *Drafting*: Define target audience, tone constraints, length bounds, and structural templates.
  * *Brainstorming*: Relax constraints to generate diverse option vectors, followed by structured filtering.

### 2. Clear & Simple Explanation

* **The Prompt Component Stack (The Blueprint)**: Writing a prompt is like writing a software function signature. Giving a vague request yields generic output. Structuring a prompt with a clear Role, Context, Task, Input Payload, and Output Specification gives predictable, high-quality results every time.
* **Task Decomposition (Breaking Down Big Jobs)**: Instead of asking the model to do five complex things in one prompt, break the workflow into smaller steps. You can run steps one after another (sequential chaining) or run independent tasks at the same time (parallel processing).
* **Diagnostic Iteration (Debugging Your Prompts)**: If an output is wrong, don't throw away the whole prompt. Treat it like code debugging: check if the constraints were unclear, if the input data was messy, or if the output format wasn't explicitly defined. Fix only the broken component.
* **Adapting Strategy by Task Type**: Customize your strategy based on the work type. For analytical tasks, make the model "think out loud" step-by-step first. For drafting, provide strict formatting boundaries and target audience rules.

### Key Technical Terms

* **Description Competency**: The core framework skill of explicitly defining task context, rules, inputs, and formats to achieve deterministic LLM execution.
* **Prompt Component Stack**: The architectural layout of a prompt comprising Persona/Role, Task, Context, Input Payload, and Output Format.
* **Task Decomposition**: System design pattern of splitting complex tasks into discrete, modular sub-tasks executed sequentially or in parallel.
* **Diagnostic Iteration**: The targeted debugging methodology of identifying and refining the specific prompt component responsible for an output error.
* **Chain-of-Thought (CoT) Prompting**: An analytical prompting technique requiring the model to generate intermediate reasoning steps prior to producing the final answer.
* **Few-Shot Examples**: Providing inline input-output reference pairs within the prompt stack to enforce strict output schema and stylistic adherence.

The lead engineer notices that while issue summaries are accurate, the generated JSON output frequently omits the required key `severity_level`. * B) Context & Background

* **Question 2**
A developer needs to build an LLM-powered financial compliance tool that evaluates 50-page credit agreements against complex statutory policies. Running the full analysis in a single prompt causes the model to hallucinate compliance passes on subtle policy breaches. Which architectural pattern best addresses this limitation?
* A) Applying few-shot examples to the main role instruction
* B) Decomposing the evaluation into parallel micro-audits per policy section, then aggregating results
* C) Increasing the system prompt temperature parameter
* D) Appending a generic "be thorough and careful" constraint to the end of the prompt

* **Question 3**
When engineering prompts specifically for analytical tasks requiring root-cause determination from complex multi-source log files, which prompting strategy yields the highest diagnostic accuracy?
* A) Mandating step-by-step reasoning (Chain-of-Thought) prior to rendering the final conclusion
* B) Restricting the output format to a single binary flag (PASS/FAIL) without intermediate text
* C) Requesting initial output in informal conversational prose to increase reasoning flexibility
* D) Omitting operational background context to prevent model bias

* **Question 4**
A developer is refactoring a monolithic prompt that attempts to translate legacy code, execute test cases, write documentation, and output a PR summary. Output quality has severely degraded due to conflicting instructions. What is the recommended Developer – Foundations recovery procedure?
* A) Switch the model tier to a lower-capability model to accelerate response generation
* B) Combine all system instructions into a single unformatted text block
* C) Perform complete rewrites of the entire prompt stack after every failed execution
* D) Decompose the workflow into a sequential prompt chain where each stage passes structured context to the next



---

### Answer Key & Explanations

* **Question 1**: **C) Output Formatting & Schema Definition**
*Explanation*: Diagnostic iteration focuses on pinpointing the specific failing component. Since the model successfully grasps the task logic but misses a structural JSON key, the Output Formatting / Schema component requires reinforcement.
* **Question 2**: **B) Decomposing the evaluation into parallel micro-audits per policy section, then aggregating results**
*Explanation*: Complex, long-context evaluations suffer from reasoning degradation when handled in a single prompt. Task decomposition breaks the policy audit into targeted, parallel sub-tasks that eliminate cognitive overload and hallucination.
* **Question 3**: **A) Mandating step-by-step reasoning (Chain-of-Thought) prior to rendering the final conclusion**
*Explanation*: For analytical and root-cause tasks, enforcing Chain-of-Thought (CoT) reasoning allows the model to map out dependencies and evaluate evidence sequentially before committing to a final conclusion.
* **Question 4**: **D) Decompose the workflow into a sequential prompt chain where each stage passes structured context to the next**
*Explanation*: Monolithic prompts attempting multi-domain tasks degrade due to instruction collision. Decomposing the task into a sequential chain ensures each sub-task receives isolated, focused context and clear boundaries.
